## Status terminology

Findings are classified using the following terms:

**OPEN**
The reported condition remains visible in current public evidence or no public repair evidence has been identified.

**PARTIAL**
Some related work has occurred, but the original finding has not met the closure standard.

**CLOSED**
A repair has been identified, deployed, regression-tested, and independently reproducible from public evidence.

**NOT PUBLICLY VERIFIABLE**
A repair may have occurred privately or operationally, but sufficient public evidence is unavailable to confirm closure.

## Closure standard

A security or protocol finding is not considered closed solely because someone states that it has been fixed.

Where applicable, closure should include:

1. identifiable repair commit or source change;
2. regression test demonstrating the original condition and repaired behavior;
3. successful build and test evidence;
4. deployed binary, contract, or configuration identification;
5. deployment or activation evidence;
6. independent reproduction or verification; and
7. a public closure record linking the evidence together.

## Responsible disclosure

This repository is intended for defensive technical documentation and public accountability.

It does not publish private keys, credentials, confidential material, or unnecessary step-by-step exploitation instructions for conditions that may remain live.

Descriptions of unresolved vulnerabilities may therefore be intentionally limited to the level necessary to document the condition and remediation status.

## No allegation of criminal conduct

Technical defects, centralized controls, incomplete disclosures, or unresolved security findings do not by themselves establish fraud, theft, malicious intent, or criminal conduct.

This repository documents technical and governance evidence and distinguishes observed facts from interpretation.
